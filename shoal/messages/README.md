# Shoal Messages

Shoal Messages is Shipwright's messenger for Sailfish OS: a native Matrix
client with a Silica interface and a protocol core built on
[matrix-rust-sdk](https://github.com/matrix-org/matrix-rust-sdk). The product
we sell is the service behind it: hosted Signal and Telegram bridges, Shoal
Push and a push gateway, and a subscription. The client is how people reach
that service.

It is a **hard fork of xmatic** by JimKnopfIoT (Apache-2.0), imported at tag
`v0.41.0`, commit `40ce16b` (see `UPSTREAM.md` for why that commit and not
v0.34.1). Licence, notices and attribution are kept: `LICENSE`, `NOTICE`,
`THIRD-PARTY.md`, and the About page, which reads "Based on xmatic by
JimKnopfIoT, Apache-2.0". Every file we changed carries "Modified by
Shipwright, 2026" and is listed in `CHANGES-FROM-UPSTREAM.md`.

## What is in the tree

```
qml/    Silica UI (Qt 5.6)
src/    C++ bridge: MatrixBridge (QObject), list models, push wake-up, settings
core/   Rust staticlib "shoal-messages-core": tokio, matrix-sdk 0.19.1,
        matrix-sdk-ui, bundled SQLite, rustls, UnifiedPush connector
rpm/    shipwright-shoal-messages.spec
docs/   PUSH.md, the user-facing push notes (shown from the app's push page)
```

Commands go into the core as JSON; events come back as JSON through one
callback, hopped onto the Qt thread with a queued `invokeMethod`. The FFI
surface is six C functions (`xm_*`, header generated by cbindgen).

| Identity | Value |
|---|---|
| Package, binary, desktop file | `shipwright-shoal-messages` |
| Sailjail `OrganizationName` / `ApplicationName` | `org.shipwright` / `ShoalMessages` |
| App D-Bus name, object path | `org.shipwright.ShoalMessages`, `/org/shipwright/ShoalMessages` |
| UnifiedPush connector name | `org.unifiedpush.Connector.ShoalMessages` |
| Data and config | `~/.local/share/org.shipwright/ShoalMessages`, `~/.config/org.shipwright/ShoalMessages/settings.conf` |
| Store key | `store.key` in the data directory, owner-only (a key in the Sailfish Secrets collection `ShoalMessages`, from before 0.1.0-8, is moved there) |
| Matrix pusher `app_id` | `org.shipwright.ShoalMessages` |

## Building

### Rust core on the host (what CI and this checkout can do)

```sh
cd shoal/messages/core
cargo build --locked          # rustup picks 1.97.1 from ../rust-toolchain.toml
cargo test --locked           # upstream's unit tests plus our distributor tests
cargo install cbindgen        # once
cbindgen --config cbindgen.toml --crate shoal-messages-core \
         --output ../src/generated/shoal_messages_core.h .
```

The host build needs a C compiler, cmake and perl (aws-lc-sys, bundled
SQLite); no gstreamer packages, since GStreamer is used only by the C++ side.

### Full RPM (Sailfish SDK)

These are upstream's documented steps with our names. Rust is built on the
host side of the SDK, not inside the scratchbox2 chroot:

```sh
# Prerequisites: Sailfish OS Platform SDK with a target, and in that target
#   gstreamer1.0-devel gstreamer1.0-plugins-base-devel gstreamer1.0-plugins-bad-devel
#   (sb2 -t <target> -m sdk-install -R zypper in ...)
# rustup with the pinned toolchain and the target triple:
rustup target add aarch64-unknown-linux-gnu    # listed in rust-toolchain.toml
cargo install cbindgen

cd shoal/messages
# Cross-builds the core with the SDK's cross gcc, stamps the version, runs cbindgen.
# Defaults: SAILFISH_SDK_ROOT=$HOME/SailfishOS-Platform-SDK, SFOS_RELEASE=5.0.0.62, SFOS_ARCH=aarch64
SFOS_RELEASE=<release> scripts/build-core.sh
mb2 -t SailfishOS-<release>-aarch64 build      # qmake links the prebuilt core; RPM lands in RPMS/
```

`scripts/build-core.sh` expects the SDK's `targets/` and `toolings/`
directories on the host filesystem (the layout of the installer-based SDK).
With the Docker build engine (`coderus/sailfishos-platform-sdk-aarch64`, as in
`docs/plan.md`), run `build-core.sh` inside the container with
`SAILFISH_SDK_ROOT` pointing at the directory that holds `targets/` and
`toolings/`, then `mb2` in the same container. The qmake project refuses to
link a core whose version stamp does not match `Version:` in the spec (both
are 0.1.0).

32-bit Sailfish 4.6: `SFOS_RELEASE=4.6.0.13 SFOS_ARCH=armv7hl
scripts/build-core.sh`, then `mb2 -t SailfishOS-4.6.0.13-armv7hl build`.

Build-time checks that run with every qmake build: `scripts/qml-check.py`
(duplicate bindings or ids in QML) and `scripts/desktop-check.py` (the two
desktop files grant the same Sailjail permissions).

## Push setup

Push is still **opt-in** (Account › Push notifications), as upstream built
it; whether the subscription onboarding should switch it on is a product
decision for the lead. When it is switched on:

- **Distributor.** The core registers with, in order: the distributor the user
  picked on the push page; `UNIFIEDPUSH_DISTRIBUTOR` if set; **Shoal Push**,
  bus name `org.unifiedpush.Distributor.shoal` (`shoal/push/distributor`);
  otherwise the first name in sorted order. The rule is
  `choose_distributor` in `core/src/push.rs`, with unit tests. The page lists
  every distributor on the bus and offers "Automatic" plus each one; the
  choice is stored as `push/distributor` in `settings.conf`.
- **Gateway.** Defaults to the hosted ntfy Matrix gateway,
  `https://push.shipwright.example/_matrix/push/v1/notify` (**placeholder
  host**). The one config location is `src/shoalconfig.h`
  (`SHOAL_DEFAULT_PUSH_GATEWAY`, overridable with a qmake `DEFINES+=`). A
  user-entered gateway is stored as `push/gateway`; clearing the field returns
  to the default, and the default is stored as "unset" so changing the
  built-in value reaches everyone who never picked their own.
- **Subscription account.** Account › Shipwright subscription takes the
  onboarding bundle from `services/deploy/provision-subscriber.sh` (pasted,
  from the clipboard, or from a file). The core (`core/src/hosted.rs`, command
  `push.configureHosted`) calls `org.shipwright.ShoalPush1.Configure` on
  `org.shipwright.ShoalPush` with the bundle's `server`, `token` and
  `topic_prefix`, then stores the bundle's `gateway` as the push gateway and,
  if push is already on, re-registers the pusher with it. If Shoal Push moved
  the registration to a new topic (`moved > 0`), the endpoint the app knew is
  stale: its pusher is deleted instead, and the fresh endpoint that follows
  (`NewEndpoint`) is registered with the new gateway (`push::after_configure`,
  tested). The app declares
  the `ShoalPush` Sailjail permission for this. If Shoal Push is absent the
  page says "Shoal Push is not installed or not running". The token never
  reaches a log, a `Debug` string or an error message. The bundle's bridge
  bots (`bridges.signal.bot`, `bridges.telegram.bot`) are kept for the
  bridges page; the Matrix part (account, initial password) is not used yet.
- **Wake-up.** Unchanged from upstream: `org.unifiedpush.Connector.ShoalMessages.service`
  D-Bus-activates the app through sailjail with `SHOAL_MESSAGES_PUSH_WAKE=1`;
  `src/pushwake.cpp` fetches the event and raises the banner without a UI.

What Shoal Push has to provide for this to work (for `shoal/push/`):

1. Own `org.unifiedpush.Distributor.shoal` on the session bus **while
   running**. The connector crate (`unifiedpush` 0.1) lists distributors with
   `ListNames`, not `ListActivatableNames`, so a distributor that is only
   D-Bus-activatable is invisible until it is started. Run it as a systemd
   user service.
2. Install `/etc/sailjail/permissions/UnifiedPush.permission`. The app's
   desktop files name `UnifiedPush`; upstream relied on the distributor's
   package (Foghorn) to supply that file. It must let the app own
   `org.unifiedpush.Connector.*` and talk to `org.unifiedpush.Distributor.*`.
   If two distributors both ship that file they conflict at the RPM level;
   coordinate the name or content with Foghorn.
3. Call the connector's `NewEndpoint` with an endpoint the Shipwright ntfy
   server serves, since the same ntfy is the Matrix gateway.

The privacy trade (gateway and push service see room and event ids and
timing, never content) is spelled out for users in `docs/PUSH.md`.

## Cover: unread count and mark all read

The cover shows `rooms with news / messages` (upstream). A `CoverActionList`
with one action (`icon-cover-cancel`) marks every unread room read; it is
enabled only while signed in with `unreadRooms > 0`. `MatrixBridge::markAllRead`
sends `rooms.markAllRead {receipt}`; the core (`core/src/readall.rs`) walks
every joined, non-space room with an unread count, a notification count or the
manual unread flag, and runs the chat list's own per-room path
(`roomlist::mark_read`: fully-read marker, public receipt only where
Privacy › "Send read receipts" is on, a private receipt otherwise), at most
four rooms at a time. The scope is the whole account, like the count; the
chat list's space filter is not applied (the cover count does not apply it
either).

## Hosted bridges: linking Signal and Telegram

Account › "Signal and Telegram" (also from the subscription page after the
bundle is applied) opens `qml/pages/BridgesPage.qml`: the state of each bridge
(not linked, linked and connected, connecting, signed out by the network),
the linked accounts with "Unlink" (press and hold, remorse), and the link
buttons. `qml/pages/BridgeLinkPage.qml` leads through the login: Signal by
QR code (scanned with the phone that has Signal: Settings › Linked devices),
Telegram by phone number, login code and, if set, the two-factor password,
or by QR code.

How it talks to the bridges: the cell's Caddy does not proxy the mautrix
provisioning API (`services/deploy/README.md`), so the app uses the bridge
bots' command interface, as a person would, in an encrypted direct chat with
`@signalbot` / `@telegrambot` (from the bundle, else on the account's own
server). Commands always carry the bridge's prefix (`!signal`, `!tg`), which
works whether or not that chat is the bot's management room.
`core/src/bridges.rs` sends `list-logins`, `login <flow>`, the step's answer,
`cancel` and `logout <id>`, and parses the bot's replies (texts from mautrix-go
`bridgev2/commands` and the two connectors) into `bridge.state` events: the
step (`qr`, `code`, `input` with its field, `done`, `failed`), the QR code as
module rows that the page draws on a `Canvas` (encoded locally with the
`qrcode` crate), and the login list with each login's bridge state. Replays of
old bot messages are ignored: only replies after the echo of one of our own
commands count (a marker field on each command). A login left over from an
earlier run is cancelled and restarted once. Typed values (phone number, code,
password) travel as `Secret` and are never logged or kept; the bot redacts the
password message itself.

Protocol: commands `bridges.status`, `bridges.login`, `bridges.submit`,
`bridges.cancel`, `bridges.logout`, `bridges.startChat` (all `{bridge, bot?}`),
events `bridge.state` and `bridge.chatReady`. Tests: a scripted bridgev2 bot in
`bridges.rs` runs the Signal QR flow (with a QR refresh), the Telegram phone,
code and password flow (wrong code, refused number), the Telegram QR flow and
cancel, unlinking, the restart of a stale login, the replay guard, and
`start-chat` (created, existing, not found, failed, not linked).

On the same phone: with Android App Support, "Open Signal/Telegram on this
phone" opens the `sgnl://linkdevice` / `tg://login` link the QR code carries
(unverified). Signal offers no link code in place of the QR code; Telegram's
phone flow is the alternative to scanning.

**Bridged rooms in the chat list.** A room of a hosted bridge carries
"Signal" or "Telegram" next to its name, before the padlock: the padlock alone
would say more than it means, because the bridge decrypts what it passes on.
`core/src/roomlist.rs` adds a `bridge` field to each row from what the room
list already holds, without loading members: the room's heroes, its
direct-chat targets and its service members (`io.element.functional_members`,
which bridgev2 sets to the bot in its portals). Any of them being a ghost
(`@signal_*`, `@telegram_*`) or the bot marks the room; ghosts of both bridges
mark nothing (`bridges::Network::of_room`, tested). `src/roomlistmodel.cpp`
exposes it as the `bridge` role, `qml/pages/RoomDelegate.qml` shows it, and
Room info says "Encrypted up to the bridge" with a line on what that means.
Privacy has a "Signal and Telegram chats" section: messages are encrypted
between the phone and the bridge, and pass through the bridge on the user's
cell readable; the bridge keeps the linked login until it is unlinked.

**First-run entry.** After sign-in, once, the home page offers
`qml/pages/BridgesIntroDialog.qml` ("Link now" opens the bridges page, "Not
now" or going back dismisses it). Both, and opening the bridges page any other
way, set `bridges/introDone` in `settings.conf`, and it is not offered again.
It waits for the home page to be on top, so it never covers the security page
or a page a link opened.

**Starting a chat by phone number.** New chat › "Choose a phone contact"
(`ContactPickerPage.qml`, needs contact matching on, since that is what reads
the address book) lists the address book's numbers; picking one opens
`BridgedChatPage.qml` with "Chat on Signal" / "Chat on Telegram" for each
linked bridge. The core puts the number in international form with the
contacts' dialling plan (below) and sends bridgev2's `start-chat`
(`!signal start-chat +491701234567`; mautrix-go v0.31.0,
`bridgev2/commands/startchat.go`, the version both v0.2609.0 bridges build
on). The bot answers "Created chat with ...: name (https://matrix.to/#/!room)"
or "You already have a direct chat with ..."; the core reads the room from the
link, joins it (`bridge.chatReady`) and the app opens it over the home page.
"Identifier `...` not found" and "Failed to resolve identifier: ..." are shown
on the page. What each bridge can find: mautrix-signal looks the number up on
Signal's servers (contact discovery), so any number with a Signal account
works; mautrix-telegram's `ResolveIdentifier` finds a phone number only in the
bridge's own table of numbers it has already seen for the linked account, so
on Telegram the page often says "Telegram found no account with this number".
Telegram usernames are not offered from the picker (the address book rarely
holds them); a Telegram contact the bridge does not know can be reached from
Telegram itself, and the chat then appears through the bridge.

When the provisioning API is proxied later (`/_matrix/provision/v3/login/...`
with the user's access token), `bridges.rs` can switch transport without
changing the protocol to the UI; the step model is the same (bridgev2 login
steps).

## Native contacts (opt-in)

Privacy › "Match people with my contacts" (off by default). When on,
`src/contactsbridge.cpp` reads the address book read-only through QtContacts
(qtcontacts-sqlite, `org.nemomobile.contacts.sqlite`, the People app's store;
Sailjail permission `Contacts` in both desktop files) and hands the core only
what can match: name, avatar URL, phone numbers, e-mail addresses, online
accounts and Matrix URLs (`contacts.setIndex`). The index stays in memory: it
is never written, logged or uploaded, and switching the option off or signing
out drops it. Changes in the address book are picked up after a short delay.

Matching (`core/src/contacts.rs`, tested): a Matrix ID stored on the contact
(`@user:server`, `matrix:u/...`, `https://matrix.to/#/@...`); for bridge
ghosts (`@signal_*`, `@telegram_*`) the `com.beeper.bridge.identifiers` in
their member event (`tel:`, `mailto:`, Telegram usernames) and a display name
that is a phone number. Numbers are compared in international form, else on
the last eight digits; a match counts only when it names one person (entries
with the same name count as one, for merged contacts). A native Matrix user's
display name never matches.

Numbers saved without a country code are read with a dialling plan
(`core/src/dialling.rs`, tested): the calling code goes in front and the
national (trunk) prefix comes off ("0170..." in Germany is +49170...; Italy
keeps its zero; the NANP's ten-digit numbers get +1; Russia's trunk prefix is
8). The country is the SIM's: `src/contactsbridge.cpp` asks oFono on the
system bus, asynchronously (`org.ofono.Manager.GetModems`, then
`org.ofono.SimManager` `MobileCountryCode` on each modem, else
`org.ofono.NetworkRegistration`'s). The `Internet` permission the app already
has grants `dbus-system.talk org.ofono`. Without a SIM (or oFono) the locale's
country is used, which is only a guess. The table
`core/data/mcc-dialling.tsv` covers every MCC in the ITU list (241): MCC to
region from AOSP's `MccTable.java`, calling code and prefixes from
libphonenumber's `PhoneNumberMetadata.xml` (v9.0.40); both are Apache-2.0, the
file names the exact revisions, and `tools/mcc-dialling.py` regenerates it.
Limits, also stated on the Privacy page: area codes are not added (a number
saved without its area code cannot be completed), and regional quirks such as
Argentina's mobile "15" are not handled. Privacy shows which country is used
and where it came from.

Where the names show: the member list and the member profile; the chat list,
where a direct chat is named after the contact (`contactName` on the row,
from the room's direct target or single hero and their display name, so a
Matrix ID saved on the contact or a Signal ghost named by its number; the
list is summarized again when the address book changes); and push banners
(`push.notify` names the sender, and a direct chat, by the contact). The
process a push wakes reads the address book before it asks for the message,
waiting at most 4 s, so the banner can name the sender. The contact picker for
bridged chats is described under "Hosted bridges".

Limitation on our cell: `bridge.phone_numbers_in_profile` is off in
`services/deploy` (ghost profiles are global on a multi-user bridge, so the
numbers would be visible to every subscriber), so `tel:` identifiers do not
arrive and phone matching works only for Signal ghosts named by their number.
Not done yet: writing the Matrix ID back to the contact (ROADMAP.md item 3).

## Subscription lifecycle hooks still to build

The bridges are hosted (see `services/`), so the client's part is small and
driven by the account's subscription state. None of this exists yet; the
file-level plan is in `ROADMAP.md`.

- **Sign-up and sign-in:** create or attach the subscriber's account on the
  Shipwright homeserver (`core/src/login.rs` already does OAuth 2.0/MAS,
  device code and password; a Shipwright homeserver preset goes on
  `qml/pages/LoginPage.qml`).
- **Entitlement check:** on session restore and periodically, ask the licence
  service for the subscription state and cache it (new `core/src/subscription.rs`,
  a `subscription.status` command in `core/src/protocol.rs`).
- **Grace and lapse:** on lapse, keep Matrix-native rooms working and tell
  the user that bridged rooms stop; the server side stops the bridges. On
  cancellation, offer bridge logout (so Signal/Telegram sessions are revoked)
  and data export before the account is closed.
- **Push tie-in:** when the subscription starts, offer to switch push on with
  Shoal Push and the Shipwright gateway; on account deletion, disable push so
  the pusher and the registration go (the existing sign-out path already does
  this).

### Review fixes and Phase 2 polish (2026-10-01, second pass)

Nothing of this has run on a device either. The Rust core was unit-tested on
an x86_64 host (173 tests, 11 of them new); the changed C++ files and their

  each portal (direct chats and groups) shows "Signal" or "Telegram" next to

  portal in particular: it is marked only if the server sends its heroes or

  completed from the SIM's country; one saved without area code is refused

- **Hosted push after a move (E-1).** With push on, apply a subscription
  bundle whose Shoal Push account moves the registration (`moved > 0`): the
  homeserver's pusher list (`GET /_matrix/client/v3/pushers`) afterwards has
  exactly one pusher of `org.shipwright.ShoalMessages`, with the new endpoint
  and the bundle's gateway, and a test message arrives.

### Phase 2 additions (2026-10-01)

Nothing of this has run on a device. The Rust core was unit-tested on an
x86_64 host (162 tests); the changed C++ files were compiled (`-fsyntax-only`,
plus moc) against the 5.2 aarch64 target's Qt 5 headers; the RPM was not
built (the release cross-build of the core ran out of shared disk twice).

- **Cover action.** Sign in, leave some rooms unread, go to the home screen:
  the cover shows the count and one action. Tap it: the count goes to 0 within
  a sync; other clients see the rooms read (public receipts) or learn nothing
  (Privacy › "Send read receipts" off: private receipts). Check that
  `image://theme/icon-cover-cancel` exists and reads as "clear", and that the
  action is absent when nothing is unread or nobody is signed in.
- **Bridges, Signal.** On a cell from `services/deploy` with a provisioned
  subscriber: apply the bundle, open "Signal and Telegram", see "Not linked".
  Link Signal: the bot's direct chat is created, the bot joins within 30 s,
  the QR code appears; wait for one refresh (about 45 s) to see it change,
  then scan it from Signal on another phone (Settings › Linked devices);
  expect "Signal is linked as +…" and "Linked and connected". Unlink with
  press and hold: back to "Not linked", and Signal's linked-device list drops
  the entry.
- **Bridges, Telegram.** Link with phone number: a number without "+" is
  refused (same field, reason shown); then a wrong code ("Incorrect code"),
  then the right one; with two-factor on, the password field is masked and
  the bot redacts the message. Repeat with the QR flow. Leave the link page
  half-way: the bot answers "Login cancelled.".
- **Bridges, robustness.** Close the app during a login and link again (the
  stale login is cancelled and restarted). An earlier QR code in the bot chat
  is never shown as the current one. The bot chat is encrypted and the bridge
  decrypts our commands (end-to-bridge encryption is on in our config).
- **Bridges, same phone.** With Android App Support and Signal or Telegram
  installed, "Open … on this phone" hands over the link.
- **Contacts.** Read `/etc/sailjail/permissions/Contacts.permission` on 5.2:
  it must grant read access to qtcontacts-sqlite's database. Switch the option
  on: the privacy page shows how many contacts were read; off: the count goes
  to 0. Save a contact with a Matrix ID (IM account or `matrix:u/...` URL)
  and check the member list and profile show the contact's name. Check
  whether the backend returns merged and per-account entries together (the
  core treats same-name duplicates as one person).
- **RPM.** Build it (`tools/build/sdk`, or `rpm/prebuild.sh` then

### From the import

Nothing below has been run on a Jolla Phone or any Sailfish device. The Rust
core was built and unit-tested on an x86_64 Linux host only; the Qt/Silica UI
and the RPM were not built here.

- The RPM builds in the Sailfish SDK Docker image with the renamed spec, and
  installs, launches and survives sailjail with the new
  `org.shipwright`/`ShoalMessages` identity (Sailjail derives the app's D-Bus
  name and data directories from that pair).
- Share target (`org.shipwright.ShoalMessages.service`), link handler
  (`shipwright-shoal-messages-open-url.desktop`) and single-instance handover
  (`src/instancelock.cpp`) work under the new names.
- The store key (`store.key`) survives restarts, and a key left in the
  Sailfish Secrets collection `ShoalMessages` by an earlier version is moved
  there when it can still be read.
- The `ShoalMessagesSpeech` Sailjail permission file is picked up (voice
  transcripts).
- Push: `org.unifiedpush.Connector.ShoalMessages` is permitted by the
  `UnifiedPush` Sailjail permission (the name no longer ends in the old
  suffix; the permission is expected to grant the whole
  `org.unifiedpush.Connector.*` namespace).
- Push: Shoal Push is found and chosen automatically; picking another
  distributor on the page registers with that one; the Silica `ComboBox` with
  a `Repeater` in its menu and its `description` line render correctly.
- Push: a message from the Shipwright ntfy gateway wakes the closed app and
  raises a banner; behaviour after reboot (no store key until first manual
  start) matches `docs/PUSH.md`.
- Subscription bundle: the `ShoalPush` permission lets the sandboxed app reach
  `org.shipwright.ShoalPush` (and `Configure` succeeds against the real
  distributor); the file picker plus `XMLHttpRequest` can read a picked
  `.json` from Documents or Downloads under Sailjail; `TextArea` with
  `Qt.ImhSensitiveData` keeps the bundle out of keyboard prediction.
- Cover and launcher icon: the placeholder artwork renders at 86, 108, 128 and
  172 px and the cover title "Shoal Messages" wraps cleanly at cover size.
- OAuth sign-in shows "Shoal Messages" and the placeholder client URI
  `https://shipwright.example/shoal/messages` is accepted by MAS (it has to be
  replaced with a real Shipwright URL before release).
- The map tile User-Agent now names a placeholder URL
  (`core/src/location.rs`); OpenStreetMap's tile policy requires a real
  contact, so replace it before release.
- Translations: the brand was replaced mechanically in 32 languages. Inflected
  forms (Finnish, Estonian, Hungarian keep the suffix; Czech, Slovak, Croatian,

  distributor", "Automatic", "Shoal Push", "Based on %1 by %2, Apache-2.0",
